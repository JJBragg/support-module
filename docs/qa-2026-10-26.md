# QA pass, everything built so far

Run on 2026-10-26 against the staging instance, by script and by hand, as
three different people: not logged in, Artur (agent), Monika (admin).

This covers the ground the 2026-10-25 pass covered, because the inbound
path has been rewritten since, plus everything added today: the board,
the columns that cannot be backfilled, six status categories, the
acknowledgement email, loop and auto-reply protection, the Spam status
and the sender blocklist.

Everything below was exercised on
<https://support-module.staging.oregon.platform-os.com>. Nothing was
tested on production, and production does not exist yet.

## Short version

Five defects found, five fixed and verified the same day. Two of them
were from today's work, one had been there since Phase 3, and two were
dead code.

Nothing lost, nobody in who should not be, no cross tenant leak. The
parts that carry the most risk, the inbound webhook, the department
scoping and the write endpoints, all held, including the five endpoints
added today.

## Fixed during this pass

**1. Reopening a closed ticket left it claiming to be solved.** Four
endpoints that change a status were moved onto a shared helper this
morning so that `solved_at` is stamped on the way in and cleared on the
way out. `commands/tickets/reopen` is a fifth caller and was missed, so
it cleared `closed_at` and left `solved_at` alone. A ticket that went
Confirmation, Closed, then reopened by a customer still said it had been
solved, at a time when it very much was not. Nothing reads the field
yet, which is exactly why it was worth catching now rather than when the
SLA engine starts reading it.

**2. The sidebar offered two filters that could only ever be empty.**
Closed and Spam were listed in the Status section with a count. The queue
holds nothing closed, so the count was always zero and clicking either
landed on "Nothing in this view", which reads like a broken filter rather
than an empty one. Closed categories are no longer listed there, which is
also what the design does. The consequence is written down below.

**3. An agent refused a ticket in another department was told it was an
Admin screen.** The 403 page knew two kinds of refusal and there are
three. An agent opening a ticket outside their departments got "This
screen is for support Admins. Your agent account can work the queue, but
not change how it is set up", which is true of a different situation and
sends them to argue with the wrong person about the wrong thing. It now
says the ticket belongs to a department their account does not cover.

**4. An agent with no departments was congratulated.** An empty queue
said "All caught up. No open tickets right now", to someone who will
never see a ticket until an Admin gives them a department. It now says
so.

**5. Dead code, including one loaded gun.** An unused `settings/update`
mutation was still in the tree: a broad `record_update` naming eleven
properties, which would clear every one the caller did not supply. The
narrow mutations that replaced it are what Settings actually uses.
Removed, along with two translation keys and one CSS class nothing
referenced.

## What was tested

| Case | Expected | Result |
| --- | --- | --- |
| Correct secret in the path | 200, ticket created | pass |
| Secret as `?token=` | 200, same behaviour | pass |
| Wrong secret, in the path or the query | 403, nothing written | pass |
| No secret at all, and an empty one | 403 | pass |
| GET instead of POST | 404 | pass |
| No sender address | 422, nothing written | pass |
| Reply with `In-Reply-To` | threads, match reason headers | pass |
| Reply with only `[#n]` in the subject | threads, match reason subject | pass |
| Reply to a closed ticket | reopens to Under Review, both stamps cleared | pass after fix 1 |
| Subject starting URGENT | opens at P0, not the default | pass |
| Recipient matching no department | falls back, does not drop the mail | pass |
| CCs on the first email | kept on the message | pass |
| Attachment metadata | filename and type kept, file not stored | pass |
| `Auto-Submitted: auto-replied` | ticket opened, no receipt | pass |
| `Precedence: bulk` | detected as automated | pass |
| Empty `Return-Path` from mailer-daemon | detected as automated | pass |

| Blocked address, and a blocked domain | 200, no ticket, no contact | pass |

The threading cascade writes its reason on every message, and the posted
header block is kept and shown behind Show original.

### The acknowledgement, 6 cases

Recorded with the ticket token in the subject, threaded to the
customer's own message, no author on it so the timeline marks it
Automatic receipt. A second one inside a day refuses. The ticket still
says it needs a reply afterwards and `first_replied_at` stays empty,
which is the point: a receipt is not an answer. Delivery reads
not_configured, honestly, because no provider is connected.

### Ticket list, 10 cases

Views, status filter, department filter, priority tabs, group by
priority, group by status, search, top three per group, See all, empty
states. Counts reconcile three ways: the priority tabs sum to the All
open total, the group headings sum to the same, and the status counts sum
to it again.

### Board, 9 cases

Columns in settings order, counts matching their cards, place in line
running across columns rather than within them (P1 showed 1 to 12 spread
over three columns, every number once), Show Closed bringing in the
closed categories and collapsing both as it goes, collapse remembered per
agent, Move to on every card, the hidden drag form, drag and drop,
confirmation before closing, Undo.

### Ticket detail, 7 cases

Timeline, private notes, quoted history, attachments as chips, the
properties panel, the composer, and the two new lines on a message: why
it landed here, and whether a person sent it.

### Settings, 7 cases

All five sections render, the status type control shows the right
category for each of the nine statuses, the blocklist shows its empty
state, departments and agents list correctly.

### Access control, 16 cases

Every refusal was checked against the data afterwards: no status was
added, no sender was blocked, no role was changed, and the P0 count was
the same before and after.

### Robustness, 8 cases

- Cross site request forgery: a note, a board move and a column collapse
  posted without a token all redirect and write nothing. Confirmed
  against the ticket's messages, its status and every agent's stored
  board state.
- Open redirect: `return_to` set to `https://evil.invalid/x`,
  `//evil.invalid/x`, `javascript:alert(1)` and `\\evil.invalid` all land
  back on the queue. A real path is honoured and keeps its query string.
- Cross site scripting: an email whose subject, body and headers carry
  `<script>`, `<img src=x onerror=...>` and a `</pre>` break-out renders
  escaped everywhere, in the list, on the detail page and inside the raw
  headers block. The only script in the document is the module's own, and
  no image was injected. Escaped exactly once: the text reads back as
  what the customer typed.
- Unknown ticket number, a non numeric one, zero and a negative all
  return a real 404. Unknown paths under /support get the host's 404.
- Every translation key the templates ask for exists. Two that nothing
  asked for were removed.

## Open, and not defects

- **An agent can mark a ticket as spam, which blocks the sender, and only
  an Admin can unblock.** Marking spam is ordinary queue work and the PRD
  gives agents status changes, but the block is a setting with a reach
  beyond the one ticket. Worth a decision: leave it, or make the block
  Admin only and let an agent only move the ticket.
- **The list has no route to closed tickets at all.** It never really did,
  since the filter was empty, but now the dead control is gone the gap is
  visible. The board has Show Closed. The list wants the same treatment,
  which is the work the board already did: load the closed ones
  separately, count the sidebar over the open ones only.
- **Priority is Admin only**, unchanged from the last pass and still worth
  deciding.
- **Over the hourly limit, inbound mail is dropped**, deliberately.

## Not tested, and why

- **Real email delivery, inbound or outbound.** No provider, no MX record.
  The receipt and the @mention email are both built and addressed
  correctly and neither has ever left the building.
- **The acknowledgement arriving in a real inbox**, for the same reason,
  and because this instance has no `test_email` in the Partner Portal.
- **Attachments as files.** Still metadata only, still the platform
  question with the engineers.
- **Phone and tablet layouts.** Phase 6. The board's own phone pieces are
  built and were checked at 375px, but the sidebar is a fixed column at
  every width, so the page as a whole is not usable there yet.
- **The superadmin break glass path**, where a host superadmin with no
  agent record counts as an Admin. Verifying it means removing an agent
  record from a live account.
- **The last admin guard.** Three Admins on staging, so it cannot fire
  without first removing two.
- **The 500 ticket queue cap and the ticket number race.** Both known,
  both need volume.
- **Collapse persistence for a superadmin with no agent record**, which
  falls back to the URL. Same reason as the break glass path.

## Still happening

The instance renders every module translation as "translation missing" on
some page loads. It was seen again during this pass, on pages whose keys
had just been deployed and on pages whose keys have been there for days.
The data on the instance is correct and the same keys resolve every time
through pos-cli. Written up as issue 5 for the engineers. Reload and it
comes back.

## Test data

The pass created nine tickets, seventeen messages, two attachments and
five contacts, all on the example.test domain, plus two blocklist
entries. Every one has been deleted, enumerated by id rather than by a
sweep. Artur's role and departments were changed twice to test scoping
and were put back.

Staging is back to its baseline: 8 tickets, 9 contacts, 9 statuses, no
blocked senders, three agents with their original roles and one
department each. The module ships no delete, so the clean up used a
record delete mutation added for the job and removed again in the next
deploy, which is the same way the last pass did it.
